# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Caly is a cross-platform PDF reader built with Avalonia UI and .NET. It targets Windows, Linux, macOS, Android, and iOS. The master branch uses NuGet packages; the develop branch uses git submodules in `external/` (run `git submodule update --init --recursive` after cloning).

## Build & Test Commands

```bash
# Build
dotnet build -c Debug
dotnet build -c Release

# Run tests
dotnet test Caly.Tests
dotnet test Caly.Tests -v detailed

# Run a single test class
dotnet test Caly.Tests --filter "FullyQualifiedName~SortedObservableCollectionTests"

# Run the printing tests (spooler tests skip unless CALY_TEST_PRINTER names a test queue)
dotnet test Caly.Printing/Caly.Printing.Tests

# Run benchmarks (Release required)
dotnet run --project Caly.Benchmarks -c Release

# Publish desktop (Release)
dotnet publish Caly.Desktop -r win-x64 -c Release -f net10.0

# Publish desktop (Native AOT; the project's AOT settings are keyed on the Portable configuration)
dotnet publish Caly.Desktop -r win-x64 -c Portable -f net10.0
```

### Single-Instance Pattern

`Caly.Desktop/Program.cs` enforces one app instance via `FileMutex`. Subsequent launches pass their file argument to the running instance via a named pipe (`FilePipeStream`).

### Rendering Pipeline

Pages are **tiled**, not drawn as vector pictures per frame:

1. `PdfPig.Rendering.Skia` renders a page to an `SKPicture`, cached per page by `PdfPageService` (`_cachePictures`, ref-counted via `IRef<SKPicture>`). PdfPig reads one page at a time per document (a FIFO `SemaphoreSlim` in `PdfPigDocumentService`), so `PdfPageService`'s request queue takes **one request at a time, in priority order**, and hands the work that needs no PdfPig (text layout, drawing thumbnails) to the thread pool. Do not run requests in parallel again: requests in flight together queue for the lock first come, first served, and a page coming into view waited behind up to 3 thumbnail or neighbour parses (seconds on JPEG 2000 pages). `IPdfDocumentService.GetPageTextLayerAsync` therefore returns the raw `PageTextLayerContent`; `PdfPageService` builds the `PdfTextLayer`.
2. `TileRenderService` (`Caly.Core/Services/Rendering/`) rasterises regions of that picture into **512 px bitmap tiles** on background threads, via its own CPU `SKSurface`. Requests are prioritised so tiles nearest the viewport centre render first. Tiles that render to nothing are recorded as bare keys ("blank"), never as images.
3. `TileCache` holds the results — thread-safe LRU, 128 MB budget by default (`CalySettings.TileCacheSizeMB`, restricted to the presets in `TileCacheSizeOptionsMB` — any other value in the file is reset to the default on load — settings Rendering tab drop-down, read once per document when its `PdfPageService` is created), ref-counted `IRef<TileImage>` so a tile cannot be freed while a render pass still draws it. The budget is **soft for on-screen tiles**: eviction skips any tile whose ref count shows a draw operation still holds it (evicting it frees nothing and would leave a hole), so when the visible tiles alone exceed 128 MB — a large screen at high zoom — the cache grows past the budget and shrinks back as tiles leave the screen. `TiledPdfPageControl.Render` also re-requests any missing exact-level tile, because tiles are otherwise only requested when the visible tile range changes: a tile evicted before its first draw would stay a hole forever. There is **one cache per open document** (`PdfPageService` is DI-scoped, and `PdfDocumentsManagerService` creates one scope per document), so host-side tile memory scales with the number of *active* documents: `PdfPageService.CancelAndClear()` (run when a document is deactivated) calls `TileRenderService.Clear()`, which cancels pending requests and empties the cache. Page detach (`CancelPage`) alone only cancels in-flight requests and keeps the cached tiles. 128 MB was chosen empirically: a realistic reading-session workload (forward scroll, a near-range back-and-forth revisit, a 100%-600% zoom cycle, more forward scroll) measured a zero-wasted-re-render floor of 48 MB and a worst-case peak of 72 MB — the LRU evicts precisely enough that budgets well below the true peak still cost no extra re-renders, so 128 MB carries a ~77% margin over the measured peak, not a razor-thin one.
4. `TiledPdfPageControl` composes the visible tiles each frame. Tile level is `ceil(log2(zoom))`, so a missing tile falls back to a coarser cached tile (upscaled sub-rect) or a block of finer ones — zoom transitions never go blank.

**Single-page view** (`PageDisplayMode.SinglePage`, per document, toolbar toggle) swaps `PageItemsControl`'s items panel for `SinglePageVirtualizingPanel`, which realises one page and is deliberately not `ILogicalScrollable`, so zoom/pan inside the page are unchanged. Because nothing off the current page is ever visible, it keeps a ±3-page picture/text-layer window (`SinglePageCacheBuffer`) instead of ±1. Picture eviction also invalidates that page's tiles, so this window is also what lets `TileCache` serve a turn back to a recently read page.

**Neighbour prefetch** (both views): on every visible-range change `PdfPageService.RefreshPages` queues the pictures of the page just before and just after the visible range (`RenderRequestTypes.PrefetchPicture`, below text layers and above thumbnails). Without it a page's parse only starts once the page is on screen, and parsing dominates: ~2–7 ms for plain text but 70–430 ms for image-heavy or scanned pages and ~2 s for JPEG 2000 pages, against 2–9 ms for the page's tiles (AOT, 16 tile workers). Prefetches live in their own cancellation generation so the scroll or turn that brings the page into view does not cancel them, and are skipped at dequeue once their page has left the picture keep window. Tiles for neighbouring pages are **not** prefetched.

Thumbnails are separate: `PdfPageService.SetThumbnail` draws the `SKPicture` into its own small CPU surface and copies out to a `WriteableBitmap`.

Rendering mode is **GPU** on desktop — Avalonia's platform default, ANGLE/D3D on Windows (`Caly.Desktop/Program.cs`). Set `"UseSoftwareRendering": true` in the settings file (`%LOCALAPPDATA%\Caly\caly_settings`) to force the software renderer; an absent key means GPU. That is the escape hatch for broken drivers. Android is still software; iOS uses the platform default.

The renderer is chosen while the `AppBuilder` is still being built, before any window and therefore before `ISettingsService` can exist, so that one key is read directly from the JSON by `JsonSettingsService.TryReadBooleanSetting` — a `Utf8JsonReader` scan over a pooled buffer that stops at the first match and never materialises `CalySettings`. It is also a property on `CalySettings` so that saving settings preserves it (`Save()` rewrites the whole file).

Tile *rasterisation* is CPU-side regardless and must stay that way — a GPU surface needs a `GRContext`, which is render-thread-owned and not thread-safe. Only the per-frame tile composition is GPU-accelerated.

GPU rendering costs roughly **+200 MB peak working set** over software on an integrated GPU (measured on `algo.pdf`, scroll/zoom): ~80 MB is a fixed ANGLE/driver floor, ~100 MB is Avalonia's full-window compositor layer (structural, not Caly-specific — only the software `FramebufferRenderTarget` skips it), and ~60 MB is actual page textures in Skia's `GRContext` resource cache, tracking visible tiles. Of that last ~60 MB, `CalySettings.UseCompactTileFormat` (opt-in, off by default) recovers roughly a third by rendering tiles as `Rgb565` (2 bytes/pixel, no alpha) instead of `Bgra8888` (4 bytes/pixel) — measured ~60 MB lower peak working set, max per-channel colour error 5/255 on a smooth-gradient test page (`P.pdf` in the PdfPig.Rendering.Skia submodule), untested against PDF content with real alpha transparency.

`SkiaOptions.MaxGpuResourceSizeBytes` is raised from Avalonia's 28 MiB default via `GpuResourceBudgetBytes` in `Caly.Desktop/Program.cs`. That budget is **process-wide** (Avalonia creates one `Compositor`, hence one `GRContext`, per process regardless of window count), so it is sized against the tiles visible at once across all visible windows — deliberately independent of `TileCache`'s per-document budget, which they must not be tied to.

Set `"Debug": { "LogRenderTimings": true }` in the settings file (or tick it in the settings Debug tab) to dump render-path timings (back-end actually in use, draw-op count, mean/max draw time) to `%LOCALAPPDATA%\Caly\logs` at exit — see `Caly.Core/Services/Rendering/RenderTimings.cs`. Like `UseSoftwareRendering` it is read straight from the JSON, and is latched at the first draw, so it applies from the next launch.

### Zoom and fit modes

`DocumentViewModel.ZoomMode` (`Manual`, `FitPage`, `FitWidth`, `FitContent`, `FitContentWidth`) is per document and bound two-way to `PageItemsControl.ZoomMode`. The view model only holds the mode. `PageItemsControl.ZoomFit.cs` computes and applies each fit, because only the control knows the viewer's size.

- **Sticky:** a fit mode stays on until a zoom is picked by hand. Zoom in/out and actual size (view model commands), and Ctrl+wheel and pinch (`ZoomPanController`), switch it back to `Manual`. Zoom changes made by a fit never touch the mode.
- **Choosing the active mode again** goes through `Manual` (`DocumentViewModel.SetZoomMode`), so it re-applies the mode and snaps the page back into view.
- **The maths** is in pure `ZoomFit`:
  - **Reference page:** the current page in continuous view, kept while scrolling so a page of another size never re-zooms. The page shown in single-page view.
  - **1 px of slack:** layout rounding at scale 1 is a bare `Math.Ceiling`, so an exact fit would round over the viewport and bring a scroll bar.
  - **10 px margin** (`ZoomFit.FitMargin`) on either side of what is fitted: the page in fit page and fit width, the content box in the content modes. Fit content also keeps it above and below the box; fit page keeps none there. Fit page shares fit width's side margins, so it never zooms past fit width. The margin also absorbs pages that end up a little wider than the fitted page, which brought the horizontal scroll bar with the slack alone: a slightly wider neighbour, or the pages panel rounding a fractional page width up to a whole pixel before the zoom scales it.
  - **Scroll bars:** the four bar states are tried in turn, and the first consistent one wins.
  - **Content cap:** content modes are capped at `max(800%, the matching page-mode zoom)`.
- **Triggers:** each requests one coalesced fit (see Timing):
  - the mode changing;
  - the `ScrollViewer`'s outer size changing;
  - an extent change (pages streaming in, a size arriving, rotation);
  - the end of a tab-switch restore;
  - `PageItem.ContentBoundsChanged`.
  A viewport-only change, such as a scroll bar toggling, never triggers. The computation uses the outer size, not the viewport, so a fit cannot chase its own scroll bars. Fits that nobody asked for act only when the zoom moves by more than 0.1%.
- **Timing:** the fit runs from `LayoutUpdated`, after the layout pass and before the frame is drawn: Avalonia's `MediaContext` runs the layout passes queued during its render callbacks before it commits, so the zoom change is laid out in the same frame. `RequestFit` invalidates the control's arrange so that a layout pass always follows a request. A job at `Loaded` priority would run after the render: the frame showing a resize or new pages would show them at the old zoom, with the horizontal bar on a shrinking window. While a zoom is in flight (`ZoomPanController.IsZooming`, cleared at `Loaded`), the fit waits for a `Loaded` job instead, as running it from layout passes would loop within the frame. A fit for a new viewer size is the exception: run from `LayoutUpdated`, whose pass has laid out the zoom in flight, it zooms at once (`TryZoomTo(..., afterLayout: true)`), so a window resize step that comes before the last step's zoom has settled is fitted in its frame too. A zoom never changes the viewer's size, so that cannot feed itself. Tests read the committed frame with `Compositor.RequestCompositionUpdate` (`PageItemsControlZoomFitMaintenanceTests.FirstFrameAfter`).
- **Tab switches:** a mode that arrives with a tab switch (`_pendingScrollToPage`) keeps the restored position unless the zoom has to change.
- **Fit zooms keep the content at the viewport's top edge in place** (`ZoomPanController.TryZoomTo(zoom, keepTopInPlace: true)`), unlike the zoom buttons, which keep the centre. Saved positions and reading anchor at the top: zooming in around the centre after opening, or after enlarging the window, pushed the top of page 1 out of view.
- **Landing:**
  - Fit page uses `GoToPage(page, 0)`, which lands on the page's top.
  - Fit content uses `GoToPage(..., PageOffsetSpace.UnrotatedPage)`, the `GoToWord` path, to centre the content box.
  - The width modes set only the horizontal offset. `GoToPage`'s `ScrollIntoView` would snap a partly visible page to its top or bottom.
  - Horizontally, fit page and the width modes put the page or its content box `FitMargin` from the viewport's left edge (`AlignWithFitMargin`). The offset is relative to the document, because an offset relative to the page stops at the page's edge. A page narrower than the viewport cannot scroll: the scroll viewer centres it.
  - In single-page view, `GoToPage` fits the target page before it lands (`FitBeforeLanding`).
- **The content box** is `PageViewModel.ContentBounds`, the page picture's `CullRect` × `PpiScale`. It is kept after the picture is evicted. Pages are recorded with an R-tree, so Skia trims the cull rect to what was *drawn*. Clips are ignored and strokes and text are bounded loosely. Scans, page-sized white rectangles, `DrawPaint` fills and soft masks (a page-sized `DstIn` draw) therefore give the whole page.
- **Opening zoom:** `CalySettings.DefaultZoomMode` (Settings > Appearance > Documents) is applied in `LoadDocumentCore`. It is `Manual` (100%) by default. Settings aren't loaded on mobile yet, so mobile always opens at 100%.

### 3D Artwork (U3D / PRC)

Work in progress. On this branch (based on master) every dependency is a NuGet package, not a submodule: PdfPig (the `PdfPig` nightly, `0.1.17-alpha-202610180035-9c18f` or later: the first with `UglyToad.PdfPig.Artwork`), `PdfPig.Rendering.Skia`, and Scene3D (`Caly.Rendering.Scene3D`, `Caly.Rendering.Scene3D.U3D` and `Caly.Rendering.Scene3D.Prc`, 1.0.0). A change to PdfPig or Scene3D is made in its own repository, published as a package, and reaches Caly by bumping the version in every project that references it. Planning documents, specs, plans and sample surveys live outside the repository in `C:\caly-work\3d\claude` (start at its `README.md`).

What exists today: **a click on U3D or PRC artwork shows the model in place on its page** (authored views, orbit/pan/zoom, play/pause/restart of U3D node animations, close). PRC meshes stored in the format's compressed form (most CAD exports: 27 of the 38 PRC samples) are decoded, all of them in the samples; a model with a compressed part that does not decode stays on its poster and says so.

Recognition:

- **PdfPig** (`UglyToad.PdfPig.Artwork`, in the `PdfPig` package): `Artwork3D.TryCreate(annotation, scanner, filterProvider, out artwork)` is the single entry point. It reads a 3D annotation (ISO 32000-2 §13.6) or the 3D asset of a RichMedia annotation (§13.7) into a read-only model: format (`U3D`/`Prc`), `GetData()` (the payload bytes, decoded on each call), authored views (`Artwork3DView`: camera matrix or U3D path, projection, background, render mode, lighting scheme, cross sections, per-node overrides), default-view resolution (`3DV` → `DV` → first view), activation settings. Views are parsed lazily; malformed entries become "absent", never exceptions. Scripts are exposed as bytes and never run.
- **`Caly.Pdf`**: `TextLayerStreamProcessor.DrawAnnotations` calls it for annotations of type `Artwork3D`/`RichMedia` only, producing `PdfArtwork3D` items carried by `PageTextLayerContent.Artworks3D` → `PdfTextLayer.Artworks3D` (`null` when the page has none, so pages without 3D pay nothing). `PdfTextLayerHelper.GetTextLayer` must not return `PdfTextLayer.Empty` when artworks exist.
- **`Caly.Core`**: `PageInteractiveLayerControl` draws a "3D" badge at the artwork's top-left corner (constant on-screen size: drawn at the inverse of the page zoom) and, on hover, a flyout with the format, the authored view names and what a click will do (`TextSelectionInputHandler.HandleMouseMoveOver` checks artworks before annotations). No badge for the artwork being viewed.

`HasNormalAppearance` is `false` for a quarter of real-world 3D annotations (no `AP` at all, or an empty one): the page shows nothing there and only the badge marks the artwork. Where a poster exists it need not picture the model: SimLab's are the view's background colour and nothing else.

Viewing in place (`Caly.Core`):

- **One view per document.** A left click on U3D or PRC artwork (`TextSelectionInputHandler.TryActivateArtwork3D` → `PageItemsControl.ActivateArtwork3D` → `DocumentViewModel.ActivateArtwork3DCommand`) creates an `Artwork3DViewModel`, sets it on that page's `PageViewModel.ActiveArtwork3D`, and closes the document's previous one. The view model reads the model off the UI thread (`IPdfDocumentService.GetArtwork3DContentAsync` under the document lock, then `Artwork3DSceneReader`), owns the `Scene` and keeps the artwork's payload. Which artwork is active is its page number and its index in `PdfTextLayer.Artworks3D`, never the `PdfArtwork3D` object: text layers are evicted and rebuilt.
- **Lighting panel**: the toolbar's sun button opens sliders (brightness, ambient, shine, highlight size, colour) bound to `Artwork3DViewModel` (`LightIntensity`, `AddedAmbient`, `SpecularIntensity`, `HighlightSizeSteps`, `DiffuseIntensity`, `ResetShadingCommand`), which makes them a `Scene3DShading` for `Scene3DControl.Shading`. They scale the file's values (100 % = as authored) and are never saved: each artwork starts from the file again, and since they live in the view model they survive the view being rebuilt.
- **The view is built on demand.** `PageItem` puts an `Artwork3DView` (the `Scene3DControl` plus a toolbar: authored views, render mode, play/pause and restart of the animation when the model has one, reset, lighting, close) into its `PART_Artwork3DHost` panel only while its page has an active artwork and is in the visual tree, like the loading skeleton. A page without 3D pays one null property and one empty panel. Leaving the tree (scrolled away, tab switched, container recycled) drops the view, which frees the GPU memory; the artwork stays active, and the view built when the page returns finds a scene without geometry, the control says `NeedsScene`, and the view model decodes the kept payload again. The camera and the animation playhead are where the user left them: the view hands `Scene3DControl.CaptureCameraState()` to `Artwork3DViewModel.CameraState` (two-way bound) as it leaves, and the next view gives it back with `RestoreCameraState` after every scene or view change until it has drawn a frame (the scene comes twice while it is built: without geometry, then read again). A state is given back only to the view it was taken from. The view forwards the control's status only while it is on a page.
- **Placement** (`Artwork3DPlacement`, `Artwork3DPlacementPanel`): the 3D control lives *inside* the page's grid, under the zoom and rotation transforms. An OpenGL control has as many pixels as its own bounds, so it is arranged at its on-screen size and given a render transform of 1/zoom; the toolbar likewise, which keeps its size on screen. Up to 3 megapixels the whole artwork is drawn (the control keeps one size while scrolling); beyond that only the page's `VisibleArea` plus a margin, with `Scene3DControl.VisibleRegion` saying which part.
- **Input**: the page's command key stays the page's (Ctrl+drag pans the page, Ctrl+wheel zooms it, also over a view: `Scene3DControl.ReservedModifiers`, and such a press hands the keyboard focus back to the page); the model pans with Shift+left-drag or middle-drag; a right-click without movement falls through to the page's context menu; the wheel zooms the model only while the 3D control has the focus (a click in the view; Esc or a click elsewhere gives it back), and `PageItemsControl.OnSinglePageWheel` leaves a focused view alone.
- **No OpenGL** (software renderer, Android, a refused GL interop): the control reports `Unavailable`; if it still does after `Artwork3DViewModel.UnavailableGrace` (3 s — a slow start also reports it, and takes it back) the view closes with "3D needs the GPU renderer." and `Artwork3DAvailability` remembers it for the run: hovers say so and clicks no longer try. A view that leaves its page meanwhile says so (`Artwork3DControlStatus.LeftPage`), which drops the pending verdict: a slow start on a page scrolled away does not turn 3D off.
- **Failures** (unreadable or geometry-less model, failed control) close the view with a warning notification; the artwork is a poster again. A U3D model that reads and has nothing to draw says why when its reader knows (`Artwork3DSceneReader.WhyNoGeometry`: a vendor extension other than `RHAdobeMeshResource`, which is decoded, or progressive detail that could not be followed). Two are PRC's own: "Part of this 3D model could not be decoded." (`Artwork3DReadResult.Incomplete`: a compressed mesh whose arrays do not come out exact, or exact geometry that could not be read; a model is shown whole or not at all) and "This 3D model has no display mesh (exact geometry only)." (`NoDisplayMesh`). What reading a model found is a verdict on the model (`Artwork3DViewModel.ModelRefusal`), unlike a failure of the document or of the control: its page keeps it (`PageViewModel.Artwork3DRefusals`, by artwork index, bound to `PageInteractiveLayerControl.Artwork3DRefusals`), hovering the artwork then gives the reason instead of "Click to view in 3D.", and another click repeats it without reading the model again.
- With `Debug.LogRenderTimings` on, the render-timings log also gives the time from a view being built to its model being drawn, and 3D frame times.

Decoding and drawing:

- **Scene3D** (NuGet packages `Caly.Rendering.Scene3D`, `Caly.Rendering.Scene3D.U3D` and `Caly.Rendering.Scene3D.Prc`, built from `CalyPdf/Caly.Rendering.Scene3D` on GitHub, branch `3d`; net8.0, BCL only; `Caly.Pdf`, `Caly.Scene3D.Avalonia`, `Caly.Scene3D.Avalonia.Tests` and `tools/Scene3DViewer` reference them, and all four must be on the same version; paths below such as `tools/Caly.Rendering.Scene3D.Prc.Generator` are in that repository): `Scene3D` is the format-neutral scene (flat pooled arrays, unified vertices, `SceneView` for a way of looking at it, a GLB writer); `Caly.Rendering.Scene3D.U3D` has `U3DReader.Read(payload)`. U3D meshes are decoded at full detail (base and progressive blocks), and line sets and point sets as meshes of line segments and points (`SceneMesh.Topology`; the control draws them unlit). What a progressive block, a line set or a point set stores is indexed in sets whose order the standard does not give and predicted in ways it gives a sentence to: the reader follows the Universal 3D Sample Software (Apache-2.0, in `C:\caly-work\3d\claude\references\u3d`; see Scene3D's THIRD-PARTY-NOTICES), and every mesh and set of its 54 sample scenes is compared with the IDTF text it was made from. A second sample set (`C:\caly-work\3d\samples-u3d-db\u3ds`, 375 files of ralovich/u3d-db; survey `C:\caly-work\3d\claude\plans\phase4-logs\u3d-db-survey.tsv`, script beside it) is checked by `U3DCorpusTests` (set `SCENE3D_U3D_CORPUS`): every file with a model gives geometry. That includes the vendor mesh `RHAdobeMeshResource` (Right Hemisphere's compressed mesh of Acrobat 3D exports, block type 0x100 or declared by a New Object Type block), decoded from Adobe's public "U3D Supported Elements" document (`U3DDocument.RHAdobe.cs`; the test asserts that a file holding such meshes yields a mesh); only files without a model (stubs) show nothing. When no node hangs on the world, nodes without a parent or under a parent that is never declared are taken as its children. **Animations** (U3D motion resources of one track + the animation modifier of a node's chain: 13 sample scenes checked against their IDTF source, 20 of the 375 files of the second set play) become `Scene.Animations` (`SceneAnimation`: keys of location/rotation/scale, loop, rate, delay); `Sample(t)` is a matrix applied *before* the node's own placement (`Sample(t) × Local`, as the reference player composes them; an exploded-view sample comes out coherent that way), `DrawList.Prepare(..., animationTime)` applies it by node name, a camera node that an animation moves, or hangs under a node it moves (the motor sample's "Animated View."), carries the camera with it: `Scene3DControl.Pose` stays as the view put it (the user steers it) and `DisplayedPose` is that pose carried by the node's animated world matrix (`ViewCamera.AnimatedWorldMatrix`/`Carry`); and `Scene3DControl` owns the clock (`HasAnimation`, `PlayAnimation`/`PauseAnimation`/`RestartAnimation`/`SeekAnimation`; autoplay when the file's modifier says so; it draws frame after frame while playing). **Skeletons** (the bones of a mesh declaration + the bone weight modifier of the node's chain + a motion of several tracks, matched to bones by name) give the node's mesh a `SceneSkin` (a mesh of its own per node; four bones and byte weights per vertex) and a `SceneBoneMotion`: `SceneSkeleton.ComputeSkinMatrices` turns a motion at a time into one matrix per bone (reference-player maths: a bone's frame starts at the end of its parent; a track changes the reference pose), `DrawList` adds them per frame (`DrawItem.SkinOffset`, `DrawList.SkinMatrices`; mesh bounds = the mesh under every bone) and the shader skins on the GPU (`aBoneIndices`/`aBoneWeights`, bone matrices in a 1024-texel-wide float texture on unit 1; `--selftest` has a "skinned square" case). Only `box_ba` of the samples has a skeleton, so the pose maths is checked against the reference code and that sample's keys, not against Acrobat. Not read: bone links, joints and limits, inverse kinematics, blending between motions, queued second motions, and the PDF's own animation settings (`3DAnimation` play count, time multiplier). The converter of the sample software drops the modifier's time scale and the motion's time offset when writing, so those two are only tested on files built in the tests; `TIME_OFFSET` is taken in seconds of the scene's clock, as the reference player subtracts it from its clock (the standard says milliseconds). `Caly.Rendering.Scene3D.Prc` has `PrcReader.Read(payload)`: the assembly tree, plain tessellation (`PRC_TYPE_TESS_3D`), compressed tessellation (`PRC_TYPE_TESS_3D_Compressed`, with its texture coordinates and colours per point), colours (a style that names no colour changes the transparency only; the colours of single faces of a compressed body come from the extra-geometry section; what an occurrence says of an item under it — its `entity_reference`, matched by file structure, type and unique id — holds for that use of the part: Removed drops the item, a style is applied over the item and its faces, and of two occurrences the outer one wins: the Turbine's colours and cutaway are only there; a reference to a single face names the body as its item does (topological context and body, from 1) and the face's number in the body, which is its number in the item's tessellation (the body's faces in the order of its shells, not the order a compressed body stores them in: read so the ABM8 crystal's pads come out as pads), and gives that face a material slot of its own (`PrcFaceGraphics.Override`); a reference that names a coordinate system (of the occurrence's file structure, counted from 1 although the standard says -1 for none) places its item in its part with it, instead of the item's own: PROSTEP's Camera lines up its display icons that way; uncompressed (`PRC_TYPE_TOPO_BrepData`) it is turned into the same model (`PrcBrepDataConverter`, phase B: topology named by number from 1 in file order per topological context; rational control points stored multiplied by their weights, a NURBS surface's for each u a run of v; an edge with no 3D curve takes its coedge's 2D curve through the surface's own parameterisation; a face with no loop is its surface over its domain); either is cut into triangles at one chord tolerance (`PrcBrepTessellator`). Rules read off the corpus, not from the draft: Hermite points are differences at half the tolerance, `RI_BrepModel` indices count from 1, a compressed NURBS's interior corrections of type 1 and 2 are in the draft's local frame of the two steps before (U/|U|, N×U, N = U×V) and those of type 3 plain coordinates (every closed net of the corpus then closes to within two quanta: `EveryClosedSplineOfTheCorpusClosesToWithinTwoQuanta`), and a topological context's `scale` (1000 or 39.37 in the corpus) takes the coordinates of its bodies to the file's. A face between two loops that each go once round a periodic surface is cut open along the seam (a strip), one loop going round a sphere or cone is a cap to the pole (a sphere's: the smaller part), a loop through a pole is expanded to a row of the parameters; a two-row sheet whose sweep step was lost is swept again along the way its face lies off it; an intersection curve is drawn through its crossing points; two loops that each go once round in v (a torus between two circles round its tube) are a strip too, and a strip may have holes; a side an iso face deduces that is an arc of its surface is recorded as that arc (`PrcEdgeSampler.Describe`: a short one has two samples, and a torus built from it needs the circle); a spline end knot repeated once more than a clamped end needs is skipped (it gave NaN); an edge just past the end of its spline patch is found on the patch's natural extension, only when the patch itself is too far; a loop that folds over itself by a sliver in the parameters (at most a tenth of its area) has the sliver cut out (`PrcLoopRepair`) and is cut again; 0.2% of the corpus's compressed faces and 0.6% of its uncompressed ones are still left out and counted (mostly spline faces whose edges lie well off their surface, and generic faces with no loop on an unbounded surface). Notes in `C:\caly-work\3d\claude\plans\2026-10-16-phase5-prc-compressed-brep.progress.md`. **Markup** (PMI notes and dimensions: `PRC_TYPE_MKP_Markup` with its `PRC_TYPE_TESS_Markup` tessellation, ISO 14739-1 7.8.8) of an occurrence is read as **hidden** nodes (a line mesh and a triangle mesh, one colour per vertex, unlit) named as PDF views name them (`<name>.<markup reference><occurrence reference>`), so a view that names a markup shows it (the WIP report's notes are one per view) and a file whose views name none shows none; some samples hold the text already outlined (polylines + triangle fills); others (the Tetra4D LandingGear's notes, Release-to-Manufacturing's dimensions) hold text entities: a string, a font named by family and size only, and the box it fills (width, height), placed by a matrix block (16 numbers column after column, after any around it): drawn in the library's own single-stroke font (`PrcStrokeFont`: printable ASCII and the common drawing signs, a box for anything else) stretched to that box, capitals as high as the box, on the baseline y = 0; a part's markups show under every occurrence that shows the part, named with that occurrence; symbol and pattern entities, blocks that place on the screen (face view, frame draw, fixed size: left out whole), markups of PRC views, leaders and annotation items are not read, nor drawn on top of the model when a markup asks. A compressed tessellation is decoded by redoing the writer's own arithmetic (`PrcCompressedDecoder`, `PrcBasis`): doubles, the standard's own length routine (a root of a sum kept in single precision), sums in the order written — **never "simplify" that code**: after a triangle of no area a decision hangs on the last bit of earlier results, and on a tube of long thin triangles one unit in the last place of one point grows into whole tolerances within a few hundred points (the 46 sample meshes that came out as shards until 2026-10-12 were one such bit: after a flat triangle only Z is kept of `MakeOrthoRep`'s axes, Y is Z ^ X with the edge's own X). - **`Caly.Pdf/Artwork`**: `Artwork3DContentReader` takes an artwork's payload and converted views out of the document (document lock required); `Artwork3DSceneReader.TryRead` turns a payload into a `Scene` and is the one place that knows which reader reads which format. `Artwork3DSceneReader.ResolveViews` must be applied to the views of a PRC model once its scene exists: PDF views name PRC nodes as `<display name>.<identifier>` (hexadecimal references to the PRC entity — in no specification, worked out from files), the scene's nodes are named the same way, and only the identifier is reliable (`PrcNodeNames`; `Artwork3DPrcCorpusTests` checks every part the sample documents' views name is in the scene).
- **`Caly.Pdf/Artwork/Artwork3DViewConverter`**: PdfPig `Artwork3DView` → `SceneView`. It reads lazily parsed parts of the view, so call it while the page is processed, under the document lock. A PDF camera looks along +Z with +X to the viewer's *left* (the files are right-handed whatever ISO 32000 says); the converter negates X and Z. A perspective scaling (`PS`) given as a number is a diameter in view-box units only above 1: writers put the number 1 there (all twelve such views of the samples), and read as a diameter it is a 179-degree lens and an empty picture. This is asserted on 88 real views that give their camera both ways (`Artwork3DCameraConventionTests`, needs `CALY_3D_SAMPLES`). What a view says of a node's visibility is said of that node alone (ISO 32000-2: "the visibility of this node"): real views hide the node of an assembly and still mean its parts to be seen, so the control's draw list passes nothing down the tree.
- **`Caly.Scene3D.Avalonia`**: `Scene3DControl`, an `OpenGlControlBase` that draws a `Scene` for a `SceneView` with orbit/pan/zoom. The highlight's exponent is `Highlight.Exponent`: 32 × reflectivity, at least 1, for U3D and PRC alike (fitted to the posters, 2026-10-22; 1 + 127 × reflectivity before, which gave the Saw's specular 0.8 a faint spot; the U3D side may be reverted after the owner's look at the SimLab models). The lighting schemes are Table 321's own (Headlamp is (0.8, 0.8, 0.9), hence a bluish cast the exporters' posters do not have). **Render modes**: the converter carries the view's `RM` into `SceneView.RenderMode`, `EdgeColor` (`AC`, black), `CreaseAngle` (`CV`, 45), `FaceColor` (`FC`, null = background) and `Opacity` (`O`, 0.5). The control draws all fifteen (the samples use Solid and SolidOutline, e.g. the Suspension at `CV` 10), in `RenderModeOverride` or the view's mode, each with the passes `Internal/RenderModePlan` lists: surfaces lit, transparent, flat or depth-only; silhouette edges; every edge, flat or shaded; vertices; node boxes. Edges come from the geometry, off the UI thread: silhouettes (`OutlineEdges`, drawn by `OutlineGpuResources` and the outline shader: kept where the faces turn opposite ways to the viewer, or meet at the crease angle or more unless the vertex normals run on unchanged across the edge, without which the Suspension's springs came out all black) and every edge per part (`WireEdges`, through a second vertex array per mesh in `SceneGpuResources`). The control keeps the scene's geometry until they are found; hosts set `PrepareEdges` when the document's views draw edges (`Artwork3DViewModel.HasEdgeViews`); a mode chosen later that needs edges for a scene without its geometry makes the control report `NeedsScene`, the view model reads the model again, and the control gives the new scene the camera and playhead it had. Our choices where the standard gives no number: ShadedIllustration adds a third of each surface's colour as emissive, box faces are lit, vertices are drawn at half a point set's size. Per-node render modes are ignored. Caly's 3D toolbar has a render-mode list (`Artwork3DViewModel.RenderMode`, `RenderModeIndex`, `RenderModeNames`): it shows the selected view's mode, goes back to it when another view is chosen, and is never saved. See its README, in particular "Things a host must know": GPU only (reports `Unavailable` under the software renderer), the scene's geometry moves to the GPU and the control reports `NeedsScene` after it left the visual tree, and `VisibleRegion` is how a zoomed page keeps the framebuffer no larger than the window. Everything with logic is GPU-free and unit-tested (`Caly.Scene3D.Avalonia.Tests`); the GL code is checked by `tools/Scene3DViewer --selftest` on a real GPU, because there is no headless OpenGL.
- **`tools/Scene3DViewer`**: opens a `.u3d`, a `.prc` or a PDF's 3D artwork; view list, render-mode list (`--render-mode M` for captures), lighting panel (Caly's sliders, `ShadingPanel`), poster beside the live view, page-zoom emulation, `--benchmark`, `--capture` (with `--poster` the poster is saved beside the capture), `--time S` (hold the animations at S seconds, for captures), `--selftest`. `Artwork3DPosterSilhouetteTests` runs it to compare a PRC model drawn through its default view with the document's poster (needs `CALY_3D_SAMPLES` and `CALY_3D_VIEWER`, the path of the built executable). Native AOT: `dotnet publish tools/Scene3DViewer -r win-x64 -c Release -p:ViewerAot=true` (not `-p:PublishAot=true`, which reaches the netstandard2.0 projects it references).

The control library is named `Caly.Scene3D.Avalonia`, never `Caly.Avalonia.*`: a namespace `Caly.Avalonia` would make the simple name `Avalonia` mean it inside every `Caly.*` namespace (it once forced `global::Avalonia.` into unrelated files).

Decisions that constrain future work: PRC's compressed tessellation (`PRC_TYPE_TESS_3D_Compressed`) comes after plain tessellation, as a phase of its own, and the text of US patent 8,207,965 is **never** used as a source for it (nor passages elsewhere that argue from it); nanoPRC (AGPL) is never to be opened; the PDF Association's PRC issues are preferred over the 2009 draft where they differ, and their decoding pseudo-code (issue #727) may be read and implemented from, but lines naming nanoPRC or the patent stay filtered out (`research/read-issue.py`) and links to either are never followed; scripts are not executed (Jint is the designated engine if that ever changes, ask first); new 3D libraries target .NET 8+ and are written for speed and low allocation; commits stay local unless told otherwise.

### AOT Compatibility

The desktop project supports Native AOT. Key constraints enforced in `Caly.Desktop.csproj`:

- `AvaloniaUseCompiledBindingsByDefault` = true in `Caly.Core` — avoid reflection-based bindings
- All assemblies are strong-name signed via `Caly.snk`

### Multi-targeting

All projects target `net10.0`. Mobile heads use `net10.0-android36.0` / `net10.0-ios`. There is no net9.0 target.
